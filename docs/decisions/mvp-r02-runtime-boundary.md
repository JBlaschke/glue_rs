# Source-selected runtime boundary and image-aware pairing

Status: accepted for bounded implementation; native calibration remains open.

The legacy owned-profile reader refuses exec transitions, unpaired attachment returns and process creation. Its fixed backend is a diagnostic context-probe transport. Reinterpreting that transport as a runtime oracle would silently discard the trusted bootstrap prefix and lose image/thread boundaries.

Add a separately named fixed runtime backend and program producer. Preserve every legacy source byte, API and rejection rule. A byte-significant profile marker selects the new program; no command-line flag can select weaker completion. Keep the existing scalar raw layout and complete error/drop/deadline/cleanup rules. A successful backend completion requires exactly one observed exec-success. Creation/spawn events are retained before explicit refusal; descendants are outside this profile.

Add an independent strict reader that consumes the raw event iterable once and validates its entire BEGIN-to-terminal-to-END transport before returning immutable facts. It retains every bootstrap event, complete provider interval, explicit attachment-boundary return and selected exec transition. It consumes exact canonical request/catalog, object READY, GO and EXEC_ATTEMPT bytes, binding their digests and protected target artifact bytes. These bytes are source-conditional evidence supplied by a trusted collector; they do not authenticate a native launch, pathname, ownership or backing object. Generic runtime catalog/argv adoption remains a separate dependency.

Only one initial attachment return may be accounted for, on the bootstrap thread before any observed entry, and only for the exact reviewed status-write/gate-read/poll routes with canonical successful return domains. It is retained as an explicitly unpaired boundary phase, never fabricated into a complete call or silently removed. All other orphan returns refuse. The bootstrap prefix must contain a successful close of the exact gate FD, a complete EXEC_ATTEMPT status write and selected execve entry. Unknown bootstrap operations, ambiguous ordering, extra threads, unsupported process creation and unmatched boundaries refuse or leave whole-result eligibility false.

Exact XNU marks the newly created exec thread for exec-success and terminates the old task. Therefore a successful selected exec correlates at the quiescent process/image boundary, not by asserting equal old/new TIDs or a syscall return. Retain its pending exec entry as a transition, with both identities, while requiring every other pending call to close. Later execs, shadow-process ambiguity, unresolved thread lifetimes and Mach routes remain explicit gaps; they never produce a clean whole capture. The new result always has native_calibration, full_trace_acceptance and state_feed_eligible false.

Controls must compare the actual compiled C producer bytes with an independent Python template, exercise selected exec with a changed TID, exact bootstrap boundary returns, complete-stream late failures, malformed/mismatched witnesses, unsupported effects and lifecycle faults, and preserve legacy refusal behavior. No provider, VM, sudo or SIP action is authorized by this decision.

Source grounds: the exact pinned XNU commit is f6217f891ac0bb64f3d375211650a4c1ff8ca1ea. In bsd/kern/kern_exec.c, exec_activate_image saves/copies the pathname before the proc exec probe; execve marks imgp->ip_new_thread using dtrace_thread_didexec, terminates the old exec task and wakes the new thread. Source scalar pointer values do not prove that pathname. The repository runner_child.c establishes READY, reads/validates the fixed GO, closes its gate exactly once, writes EXEC_ATTEMPT and invokes execve with its compiled catalog path. bootstrap_io.c supplies the bounded poll/read/write routes. Exact source anchors and retained hashes accompany the module README/control receipt.
